# 👗 Стилист — ИИ-агент подбора образов

Агент собирает готовый образ из каталога одежды под конкретного человека: учитывает
цветотип, вкус, повод, бюджет и размеры. Отвечает и на вопросы по стилю — по базе
знаний из 69 правил (колористика, фигуры, дресс-код, трендовые приёмы).

Архитектура повторяет учебный проект Workshop 1: тонкий API-слой, сервис-оркестратор
и слой агента за абстрактными интерфейсами.

> Предыдущая версия проекта (мультиагентный граф на LangGraph, RL-персонализация,
> LangFuse) описана в [docs/README-graph-version.md](docs/README-graph-version.md).
> Её код доступен в истории git — коммит `f68aa5e`.

## Быстрый старт

Нужны Python 3.12+ и Node 18+. Ключи API **не нужны** — приложение работает
на встроенных эвристиках.

**1. Бэкенд** (терминал 1):

```bash
cd backend && python3 -m venv .venv && .venv/bin/pip install -r requirements.txt
```

```bash
cd backend && .venv/bin/uvicorn app.main:app --reload
```

**2. Фронтенд** (терминал 2):

```bash
cd frontend && npm install && npm run dev
```

Откройте http://localhost:5173 — документация API на http://localhost:8000/docs

## Как это устроено

```
Стилист/
├── backend/          FastAPI + SQLite
│   ├── app/
│   │   ├── api/          HTTP-эндпоинты
│   │   ├── services/     оркестрация: профиль → агент → сохранение
│   │   └── agent/        «мозг»: не знает про HTTP и БД
│   ├── data/             каталог вещей (JSON)
│   └── knowledge_base/   правила стиля (markdown)
└── frontend/         React + Vite + TypeScript
    └── src/
        ├── pages/        Подбор образа · Профиль
        ├── components/   карточки вещей, бейджи
        ├── api.ts        клиент к бэкенду
        └── types.ts      зеркало схем бэкенда
```

### Путь запроса

```
Пользователь пишет «собери образ на свидание до 12000»
   │
   ├─ StylistService  поднимает профиль пользователя из БД
   │
   ├─ Агент
   │     1. понять запрос      интент, бюджет, повод, ограничения
   │     2. обогатить профиль  внешность и вкус из фото
   │     3. развилка:
   │          вопрос  → поиск по базе знаний → совет
   │          образ   → каталог + сборка по слотам
   │          не вышло→ сказать, чего не хватает
   │
   └─ StylistService  сохраняет профиль и запись в историю
```

Три возможных ответа агента видны в интерфейсе бейджем: **Образ собран**,
**Совет стилиста**, **Нужны данные**.

## Данные

| Что | Где | Как менять |
|---|---|---|
| Каталог вещей | `backend/data/catalog.json` | отредактировать JSON и удалить `backend/stylist.db` |
| Правила стиля | `backend/knowledge_base/*.md` | дописать абзац; каждый абзац — отдельный фрагмент для поиска |

Формат правила: жирный список тегов, затем сам текст. При поиске совпадение с
тегом весит больше, чем совпадение в тексте, — поэтому правило и находится.

```markdown
**зима, цветотип, палитра.** Зимнему цветотипу идут чистые холодные цвета…
```

## Настройки

Все параметры — в `.env` (шаблон: `.env.example`). Ключевые:

| Переменная | По умолчанию | Смысл |
|---|---|---|
| `STUB_LLM` | `true` | `true` — без обращений к модели, на эвристиках |
| `STUB_VISION` | `true` | `true` — фото не анализируются, берутся типовые значения |
| `LLM_API_KEY` | — | ключ провайдера (нужен при `STUB_LLM=false`) |
| `LLM_BASE_URL` | `https://api.openai.com/v1` | для OpenRouter: `https://openrouter.ai/api/v1` |
| `AGENT_TYPE` | `simple` | `stub` — заглушка, ничего не подбирает |

**Внимание:** при `STUB_LLM=false` каждый запрос идёт к платному API.

### Включить настоящую модель

Из коробки проект работает **без ключей**: разбор запроса идёт на эвристиках,
анализ фото возвращает типовые значения. Ничего настраивать не нужно.

Чтобы задействовать LLM, создайте `.env` и укажите свой ключ:

```bash
cp .env.example .env
```

Затем в `.env`: `STUB_LLM=false` и `LLM_API_KEY=sk-...`. Разница видна на
запросах вроде «тысяч на 9» или «бюджет 15к» — эвристика такие формулировки
не разбирает, модель разбирает.

## Ограничения

Честно о том, что в проекте намеренно упрощено:

- **Каталог — 13 вещей** из файла `data/catalog.json`, не живой API магазина.
  Поэтому на узкий бюджет подбор бывает грубоват: подходящей вещи может просто
  не оказаться в наличии. Как это решается — в разделе «Что дальше».
- **Поиск по базе знаний — TF-IDF**, без эмбеддингов. Работает за счёт
  кураторских тегов у правил; на синонимах, которых нет в тексте, промахнётся.
- **Анализ фото не подключён к интерфейсу** — загрузки картинок в UI нет,
  vision вызывается только программно.
- **Авторизации нет**: пользователь определяется идентификатором из браузера.

## Что дальше

Текущая версия — работающий каркас на упрощённых данных. Развитие идёт по двум
главным направлениям: **откуда берутся вещи** и **откуда берётся вкус**.

### 1. Масштабирование каталога

Сейчас каталог — это 13 записей в JSON-файле, снимок «как если бы». В рабочей
версии он должен стать настоящим ассортиментом с фотографиями. Два пути, они
не исключают друг друга:

**Собственные базы товаров.** Несколько крупных баз с изображениями вещей,
наполняемых из фидов магазинов и обновляемых по расписанию. Плюс — полный
контроль над разметкой: можно хранить свои теги силуэта, фактуры, посадки,
которых нет в исходных данных магазина, и на них опирать подбор. Минус —
данные устаревают между обновлениями, наличие и цену нужно перепроверять.

**Коннекторы к витринам магазинов через MCP.** Вместо копирования каталога к
себе — обращение к маркетплейсам в момент запроса: наличие, размер и цена
приходят актуальными. MCP (Model Context Protocol) даёт для этого единый
протокол: каждый магазин подключается как отдельный источник, а агент работает
со всеми одинаково, не зная про особенности конкретного API. Тогда добавление
нового магазина — это подключение коннектора, а не переписывание кода.

Архитектура к этому готова: агент обращается к каталогу через интерфейс
`Catalog` ([agent/base.py](backend/app/agent/base.py)), и текущая реализация
поверх БД — лишь одна из возможных. Коннектор к магазину встанет на то же
место, остальной код не изменится.

### 2. Обучение вкусу по картинкам из Pinterest

Самая слабая часть любого стилиста — понять, что человеку на самом деле
нравится. Словами это описывается плохо: «люблю минимализм» у разных людей
означает разное.

Pinterest решает эту проблему естественно — люди уже собирают там доски с
образами, которые им нравятся, без всякой просьбы со стороны сервиса. Идея:
подключить доску пользователя, прогнать изображения через vision-модель и
собрать из них профиль вкуса — палитру, силуэты, стилевые направления,
повторяющиеся приёмы. Не одно фото, а десятки, поэтому выводы получаются
устойчивыми: случайная вещь не перевесит общую закономерность.

Механика уже заложена: `Vision.profile_taste` принимает список изображений и
возвращает `StyleProfile`, а `StyleProfile.palette` весит в подборе больше,
чем цветотип ([agent/outfit.py](backend/app/agent/outfit.py)) — то есть
устойчивый вкус человека сознательно ставится выше общих правил колористики.
Не хватает только источника картинок: сейчас это ручной список ссылок, должна
стать доска Pinterest.
